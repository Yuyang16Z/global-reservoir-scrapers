# Japan — Gunma Prefecture dams (hourly, mobile edition)

7 prefectural dams — 坂本, 霧積, 塩沢, 四万川, 道平川, 大仁田, 桐生川 — each publishing
all four priority variables on an hourly 25-point rolling window.

## Finding the entry point

The desktop site is not readable. `www.river-gunma.jp/gunma/top/10/1_0_1_0.html`
renders dam readings only into `<img alt="">` text (`坂本ダム:貯水位 520.73m`) with **no
observation timestamp**, and its navigation is generated by `riverMap.js` at runtime,
so no dam URL appears in the landing HTML. Querying the DOM for `onclick` handlers
matching the site's own `changeMenu` navigation function returned nothing — the menu is
built on hover.

The site's **mobile edition**, linked from the desktop page, serves plain Shift_JIS
pages with a stable path scheme. Every URL below came from a link on a fetched page;
none was guessed (guessed desktop paths returned 404 across the board):

```
/k/                        → ダム情報  /gunmaT/m4001/10/_0_1_0.html
/gunmaT/m4001/…            → one link per dam, index 1..7
/gunmaT/m4101/{10,60}/…    → 現況表: all four variables, LATEST VALUE ONLY
/gunmaT/m4102/{10,60}/…    → 貯水位   time series
/gunmaT/m4103/{10,60}/…    → 流入量   time series
/gunmaT/m4104/{10,60}/…    → 放流量   time series
/gunmaT/m4110/{10,60}/…    → 貯水量   time series
```

The 現況表 carries no history, so the four per-variable pages are fetched instead:
7 dams × 4 variables = 28 requests, 25 hourly points each. `/60/` (hourly, 24h span) is
used over `/10/` (10-minute, 4h span) because the window must survive a daily run.

## Two markup variants in one system

`m4103` (inflow) is laid out differently from its three siblings:

| page | row markup |
|---|---|
| m4102 / m4104 / m4110 | `<TD>09/09</TD><TD>09:00</TD><TD>520.73→</TD>` |
| m4103 | `<TD>09/09 09:00</TD><TD>5.60</TD><TD>↑</TD>` |

A fixed cell pattern written against the first variant parses **zero** rows from the
second — and did, silently, on the first run: inflow came back empty for all 175 rows
while the other three variables were complete. Rows are now read cell-by-cell, and a
page yielding zero points is reported as a problem rather than passing quietly.

A value must fill its **whole** cell (optionally followed by a trend arrow). That
anchoring is load-bearing: strip the punctuation out of the combined `09/09 09:00`
cell and it becomes `09090900`, which `float()` accepts without complaint.

## Two guards

- The dam is identified by the name **printed on the page**, never by the index in the
  URL. If the site reorders its list, rows follow the name.
- Each page declares its own variable in the header (`ダム貯水位`, `流入量(時間)`,
  `ダム放流量`, `ダム貯水量`). That declaration is **asserted** against the variable the
  URL was fetched for; a mismatch drops the page and is reported. This is the same
  header-label discipline the servlet-family scraper needed after positional column
  mapping was caught writing 流入量 into `water_level_m`.

## Units and verification

As declared by each page: 貯水位 m (masl), 流入量/放流量 m³/s, 貯水量 千m³ → ×0.001 → mcm.

Checked against the independent 現況表 page at a shared timestamp — 12/12 exact,
including the storage conversion:

| dam | 貯水位 | 貯水量 (千m³ → mcm) | 流入量 | 放流量 |
|---|---|---|---|---|
| 坂本ダム | 520.72 = 520.72 | 513 → 0.513 | 4.18 = 4.18 | 4.18 = 4.18 |
| 四万川ダム | 729.70 = 729.7 | 1,399 → 1.399 | 4.54 = 4.54 | 4.88 = 4.88 |
| 桐生川ダム | 243.81 = 243.81 | 4,244 → 4.244 | 11.54 = 11.54 | 11.28 = 11.28 |

## Overlap with existing Japanese sources

**All 7 dams are new.** Checked by exact Japanese name against the 127-dam MLIT/OpenGov
delivery: no match. Gunma's nationally managed dams (矢木沢, 下久保, 藤原, 相俣, 薗原,
草木, 奈良俣, 八ッ場) are in that delivery and are *not* served by this prefectural
system, so there is no de-duplication to do here.
